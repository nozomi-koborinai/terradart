If you are deciding whether to depend on TerraDart, two questions matter more
than any feature list: *why should I trust hundreds of generated factory
classes?* and *why should I expect this project to keep up with Google Cloud?*
This page answers both with mechanisms you can inspect in the repository —
every claim below names something that actually runs, not an aspiration.

## The generation pipeline

Curated factories are not written by hand. They are generated by a maintainer
CLI (`terradart wrap`) from two pinned inputs:

- the **Terraform provider schema** for `hashicorp/google`, checked in as a
  fixture and bumped deliberately, and
- **Magic Modules metadata** — the upstream YAML Google uses to generate the
  provider itself — synced per-resource with provenance recorded for every
  file.

The two inputs merge into an intermediate representation, and the wrapper
emitter renders Dart from it: constructors mirroring the schema, typed enums
where the provider documents finite values, typed helper classes for nested
blocks, and doc comments distilled from upstream descriptions.

Generation is **byte-deterministic**. A CI gate re-runs the generator against
the pinned inputs on every pull request and fails if a single generated file
differs from what is committed. There is no "mostly generated, occasionally
hand-patched" gray zone: generated files carry a do-not-edit banner, repo
tooling blocks direct edits to them, and the only way to change one is to
change its inputs and regenerate. The parser that extracts enum values from
schema descriptions is the same code the coverage checker runs — the
generator and its auditor cannot drift apart.

## The curation philosophy

A generated binding is only as good as the judgment applied on top of it.
TerraDart's rule is simple: **facts are derived, judgment is declared, and
both are auditable.**

- Anything the provider schema or Magic Modules can state — parameter sets,
  enum values, output getters, nested block shapes, class documentation — is
  *derived*, so it moves automatically when upstream moves.
- The human decisions — which resources to curate, how to model an
  exactly-one-of block as a sealed class hierarchy, which surfaces to freeze
  deliberately — live in thin, reviewable override files, not scattered
  through generated code.
- Every escape hatch is a **fail-closed ledger**: skipped examples, frozen
  enum surfaces, cost classifications, and coverage debts are recorded lines
  with reasons, and CI fails when a ledger entry goes stale. Deleting a line
  is a reviewed decision; forgetting one is impossible to do silently.

This is also why the API is opinionated in places: IAM adjuncts default to
`*_iam_member` (additive) rather than authoritative `binding`/`policy`
variants, and mutually-exclusive nested blocks are enforced at compile time
with sealed classes instead of documented conventions.

## The verification harness

Type-checking generated code proves it compiles, not that it works. TerraDart
layers verification from cheap to expensive:

- **Synthesis gates.** Every quickstart example is synthesized in CI. A gate
  fails if any curated factory stops appearing in at least one example's
  output, and an API-enablement graph check fails if an example enables one
  Google API but forgets another that its resources need at apply time.
- **Determinism and audit gates.** The byte-identity check on generated code,
  an override linter (dead configuration, unenforced exactly-one groups), an
  enum-coverage checker strict down to nested blocks, and a fingerprint check
  that catches mislabeled upstream provenance — all per pull request.
- **Real applies.** `terraform validate` cannot catch apply-time problems, so
  TerraDart maintains a dedicated GCP project where apply-eligible examples
  are **actually applied and destroyed**: automatically on any pull request
  that touches an example, and as a monthly full sweep. Cost is governed by a
  default-deny ledger — a resource type nobody has classified for billing
  simply does not get applied.

When you upgrade TerraDart and your synthesized JSON is unchanged, that is
not luck; it is the property the whole harness exists to protect.

## Sustainability

TerraDart is a **single-maintainer project**, and you should weigh that
honestly. Here is what makes it a smaller risk than the label suggests:

- **The update loop does not depend on the maintainer being present.**
  Provider schema updates arrive as automatic weekly pull requests. A
  scheduled agent triages each one — classifying it, applying mechanical
  repairs, or escalating anything that needs human design judgment — and
  merging is guarded by an independent mechanical gate (an allow-list of
  touchable paths plus the full CI battery), not by anyone's mood. Routine
  Google Cloud drift is absorbed on a cadence, unattended.
- **The repository is deliberately maintainable by others — human or AI.**
  A single agent guide is the source of truth for how to work on the
  codebase; the ledgers make every standing decision explicit; determinism
  makes every regeneration verifiable. A successor does not need to
  reverse-engineer tribal knowledge to take over, and most routine
  maintenance is already performed by agents under the gates described
  above.
- **Lock-in is shallow by design.** TerraDart's output is standard Terraform
  JSON. If the project stopped tomorrow, your existing configurations would
  keep working with plain `terraform apply` — and migrating away is a
  file-format decision, not a re-architecture.

What is *not* promised: there is no SLA. Issue triage and reviews are
best-effort, and security response targets are documented in
[SECURITY.md](https://github.com/nozomi-koborinai/terradart/blob/main/SECURITY.md).
The [status page](/docs/status/) states the current release phase and change
policy in the same spirit.
